# Task Closeout

把“已经做完”转换成有证据的收尾结论。只审查当前会话；用户要求跨会话审查时，使用其提供的固定点、文件或任务记录，不猜测缺失历史。

## 工作流

### 1. 重建范围

从用户的原始要求、后续修正、工具记录和当前状态建立基线清单：

- 修改或新增的文件及其归属
- 完成的任务
- 影响结果的重要判断
- 已知未解决问题
- 需要人工确认的内容

以会话记录确定本次工作的归属，再用实际文件、diff、配置、日志或外部只读回读核验。已有或无法归属的改动标为“既有”或“未知”，不计入本次成果。

完成标准：每项原始要求都能映射到已完成内容、待处理问题或明确的非目标。

### 2. 只读复查

在形成完整问题清单前不继续修改。切换到审查者视角，逐项寻找：

- 遗漏的原始要求
- 明显的逻辑、内容或集成错误
- 不必要或超出范围的修改
- 应执行但尚未执行的验证
- 缺少证据、无法确认或可能失效的假设

说明每个发现的证据、原因和影响。高风险任务涉及安全与权限、数据删除、生产配置、外部写入、资金或隐私、共享契约或大范围改动时，若独立代理可用且复核能增加实质信心，安排一次独立只读复查；只提供原始要求和原始证据，不提供预设结论。主代理核验其发现。

### 3. 修正并复查

对原请求已授权范围内、能够安全处理的问题直接做最小修正，然后重新检查受影响部分。保留“发现后已修正”的记录。

需要扩大范围、新增生产依赖、改变重大设计、执行破坏性操作或新增外部写入时停止并请求决定。外部操作只做只读回读；除非原授权明确覆盖重复写入，否则不以重放写入作为验证。

只要仍有安全且有证据的推进路径就继续。相同阻塞重复出现、需要新的权限或外部状态、或无法取得新证据时停止并如实报告。

### 4. 执行验证

选择最接近改动行为的检查，并记录实际命令或方法、结果和覆盖范围：

| 任务类型 | 优先验证 |
|---|---|
| 代码 | 受影响测试、类型检查、lint 或 build；完整验证成本过高时运行最小 smoke test |
| 文档、UI、媒体 | 渲染或打开实际产物，检查内容、布局、交互、编码和目标规格 |
| 配置、数据、脚本 | 使用解析器、schema、dry-run 或最小输入输出检查 |
| 外部操作 | 对准确目标执行只读 API、日志或界面回读 |
| 调研与分析 | 核对要求覆盖、来源质量、引用对应关系和时效性 |

代码任务至少执行一项可运行的相关检查；没有任何可执行检查时不得判为 `PASS`。验证发现的新问题返回第 3 步处理，修正后重新运行相关检查。

验证失败时保留真实错误并区分实现问题、环境限制和既有无关失败。无法验证时说明原因、替代检查和具体的后续验证方法，不把“未发现问题”写成“验证通过”。

### 5. 输出收尾报告

最终回复必须自包含，并使用以下五部分：

1. **本次工作**：文件、任务和关键判断。
2. **审查结果**：已修正问题、剩余问题及原因；没有发现时明确写“未发现问题”。
3. **验证结果**：实际检查、结果和覆盖范围。
4. **结束前需知**：只列尚需注意的风险、假设、人工确认和下一步，不重复已完成内容；没有时明确写“无”。
5. **最终状态**：只使用以下一个状态。

| 状态 | 判定 |
|---|---|
| `PASS` | 原始要求已覆盖，相关验证通过，没有已知剩余问题 |
| `PASS_WITH_CONFIRMATION` | 自动检查已完成，只剩边界清楚的人工确认 |
| `NEEDS_WORK` | 已知缺陷或遗漏仍存在，当前不能继续在原范围内处理 |
| `BLOCKED` | 缺少权限、环境、输入或关键证据，无法判断或验证正确性 |

最终结论只代表“在已执行检查范围内未发现剩余问题”，不声称绝对没有问题。
